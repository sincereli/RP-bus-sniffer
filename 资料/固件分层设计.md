# 固件分层设计

> 本文定的是**固件的分层骨架与核心接口**，不涉及具体实现。接口的权威定义在
> `RP_Bus_Sniffer/{app,middleware,protocol,hal,bsp}/` 下的头文件里，本文只解释
> 为什么这样切、以及新增一个协议要做什么。

## 1. 设计目标

**加新协议时不改上层。** 具体到代码：新增一个协议只能新增文件、外加一行注册，
不能修改应用层、中间件层、HAL 的既有逻辑。

这条约束决定了两件事：

1. **上层不认识任何具体协议。** 中间件里不允许出现 `switch (proto_id)`，应用层的
   菜单也不能硬编码协议列表——否则漏点会从中间件挪到应用层。
2. **协议差异在协议层内部消化。** UART 的字节流、I2C 的事务、SPI 的原始时序、
   RTT 的文本行，各自定义自己的结构体，由各自的编码器转成统一格式。

## 2. 四层划分

| 层 | 目录 | 职责 | 不知道什么 |
|---|---|---|---|
| 应用层 | `app/` | 工作模式状态机、菜单、屏幕、摇杆、上位机会话 | 不知道总线时序与协议字段 |
| 服务与中间件层 | `middleware/` | 记录编码分发、落盘、时间戳、USB、config.txt、掉电保护 | 不知道具体协议 |
| 协议引擎层 | `protocol/` | SPI/I2C/UART/SWD-RTT 的采集、解析、主机读写 | 不知道屏幕和文件长什么样 |
| 硬件抽象层 + 板级资源包 | `hal/`、`bsp/` | 总线线路与角色、PIO/DMA 资源分配、引脚与时钟、复用器 | 不知道协议语义 |
| 底层驱动与芯片外设 | `drivers/` | PIO 程序、DMA、GPIO、定时器、ADC、RTC、USB/SD 控制器 | 不知道业务 |

注意第三层包含两个目录：`hal/` 是与板无关的抽象接口，`bsp/` 是它在某块具体板子上的
落地。换板只改 `bsp/`。

## 3. 数据主通路

```
   协议引擎                  中间件                        消费者
 ┌──────────┐  原生记录   ┌──────────────┐  统一记录   ┌─────────────┐
 │ spi_engine│ ─────────> │ log_emit()   │ ─────────> │ storage sink │ TF 卡
 │ i2c_engine│            │  查编码器    │            │ usb sink     │ 上位机
 │ uart_engine│           │  encode()    │            │ summarize()  │ 屏幕
 └──────────┘             └──────────────┘            └─────────────┘
        │                         ▲
        │ 申请 PIO/DMA/总线        │ 启动时注册 proto_module_t
        ▼                         │
 ┌──────────┐              ┌──────────────┐
 │ hal/bus  │              │ proto_registry│
 │ hal/pio  │              └──────────────┘
 └──────────┘
```

中间件只看 `proto_id`，负载对它是不透明字节块。TF 卡与 USB 共用同一份序列化
格式（见 `middleware/record.h` 的"线上序列化格式"），PC 端只需要一套解析代码。

## 4. 核心契约

| 契约 | 头文件 | 一句话 |
|---|---|---|
| 统一记录 | `middleware/record.h` | 时间戳 + 协议号 + 标志 + 负载，以及线上序列化布局 |
| 编码器 | `middleware/log_codec.h` | `hdr_build` / `encode` / `summarize` 三个函数 |
| 日志扇出 | `middleware/log.h` | `log_emit()` 投递；sink 注册后自动分发 |
| 协议模块 | `protocol/engine.h` | 把监听引擎、主机器、编码器、参数打包注册 |
| 协议注册表 | `protocol/registry.h` | 查找/遍历；菜单从这里生成 |
| 总线抽象 | `hal/bus.h` | 线路、角色（高阻/监听/主机）、电平方位 |
| 资源分配 | `hal/pio_alloc.h` | 统一分配 PIO 状态机与 DMA 通道 |
| 板级接口 | `bsp/bsp.h` | 引脚来源、复用器、上拉、电量、指示灯 |

## 5. 新增一个协议要做的事

以加 I2C 为例，完整清单：

1. 新建 `protocol/i2c/`，实现：
   - `i2c_engine.c`：PIO 状态机采样 + 帧解析，实现 `engine_ops_t`
   - `i2c_codec.c`：实现 `record_codec_t` 的三个函数
   - `i2c_cfg.c`：实现 `proto_cfg_ops_t`（7/10 位地址、速率、上拉…）
   - `i2c_master.c`（可选）：实现 `bus_master_ops_t`
2. 在 `protocol/registry_builtin.c` 的 `proto_init()` 里加一行
   `proto_register(&i2c_module);`
3. 在 `CMakeLists.txt` 里加源文件

**不需要改**：`middleware/`、`app/`、`hal/`、`bsp/`。

例外情况——加协议时确实要动共享头文件的地方，只有两处，都是**纯追加**：

- `middleware/record.h` 的 `proto_id_t` 末尾加一个枚举值（不许复用旧值，
  否则旧日志会被按新协议解析）；
- 如果需要新引脚，在 `bsp/` 的引脚表里加。

## 6. 初始化顺序

必须按这个顺序，否则会出现资源未初始化或总线驱动冲突：

```
bsp_init()            时钟、GPIO 默认态、复用器置安全位
  -> hal_pio 记账清零
  -> tb_init()        时间基、RTC
  -> pwr_init()       电压监测
  -> storage_init()   挂载 TF 卡
  -> usbdev_init()    USB 复合设备
  -> cfg_load()       config.txt
  -> proto_init()     各协议模块注册（此时只登记，不申请硬件）
  -> log_attach_sink(storage_sink()) / log_attach_sink(usbdev_sink())
  -> app_init()       进入 IDLE 模式
```

**注册与申请硬件分开**：`proto_init()` 只把模块登记进表，真正申请 PIO/DMA 发生在
引擎的 `open()`。这样上电不需要预先占用资源，也可以只启用用户选中的那一个协议。

## 7. 模式切换顺序

```
旧引擎 close()  ->  bus_release(旧)  ->  log_close()
   ->  bus_setup(新)  ->  新引擎 open()  ->  log_open()
```

必须先释放再申请：两个引擎抢同一组 PIO/DMA 会直接失败，两个方向同时驱动总线
则是电气冲突。

## 8. 现有代码的迁移映射

当前固件是在验证阶段写的，还没有按分层重排。迁移时的对应关系：

| 现有位置 | 迁往 | 说明 |
|---|---|---|
| `RP_Bus_Sniffer.c` | `app/` + `main.c` | 屏幕刷新、mailbox 抽取属于应用层 |
| `board.h` | `bsp/` | 引脚与系统参数 |
| `drivers/sniffer/` | `protocol/spi/` | 它本来就是协议引擎，不是驱动 |
| `drivers/sdcard/` | `drivers/sdcard/` | 保持为底层驱动，FatFs 封装上移到 `middleware/storage` |
| `drivers/st7789/` | `drivers/st7789/` | 最终产品是 I2C OLED（见 `资料/项目.md` H-04） |

**迁移尚未开始，当前构建仍然使用旧目录**，新的头文件没有被任何源文件包含，
所以不影响现有固件编译。

## 9. 留给实现阶段决定的事

- 各协议负载的具体字段布局（编码器内部格式，版本号记在会话元数据里）。
- `log_emit()` 的编码缓冲大小与丢弃策略（当前按 4KB 预留）。
- Core 0 / Core 1 的任务划分在分层之后的落点：中间件的 sink 写卡在 Core 0，
  协议引擎的采集在 Core 1，`log_emit()` 必须能从 Core 1 调用。
- UI 的具体界面与菜单树（应用层内部，不影响其它层）。
